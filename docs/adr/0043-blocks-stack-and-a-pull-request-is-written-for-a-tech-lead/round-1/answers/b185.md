# b185 : feat(webapp): the archive uploads

## 1. Contexte

Le lot « the data travels » ajoute à l'écran du compte un import d'archive dont l'upload résiste à une coupure réseau et à un changement d'écran. #222 a posé le store d'upload (au-dessus du routeur, un `PUT` de chunk à la fois) et la fonction pure de `lib/imports.ts` qui décide chaque étape (append, réconciliation sur `409`, retry, pause, arrêt) ; #223 a donné à la section Import son côté lecture (dernier import, son état, annulation confirmée). Ce qui manque : rien n'appelle encore le store, donc aucun utilisateur ne peut démarrer un import.

## 2. Pourquoi

Sans ce consommateur, le store et la logique de #222 sont du code mort côté utilisateur : pas de sélecteur de fichier, pas de vue de progression, pas de message quand l'upload s'arrête. Cette PR rend le parcours d'import utilisable de bout en bout et le couvre par un journey qui pilote toute la boucle à travers l'écran. Le « maintenant » est surtout de séquencement : c'est le dernier tiers du bloc 30, découpé en trois parce qu'il mesurait 892 lignes (au-delà du budget de bloc). La description ne dit pas ce qui casserait d'autre sans elle.

## 3. Comment

La section lit deux sources dans cet ordre : d'abord l'upload tenu par l'onglet (qui survit à l'écran), sinon le dernier import du serveur, ce qui décide entre barre de progression/pause/refus, le sélecteur de fichier ou l'état en cours de #223. Le sélecteur attend le handshake (bloc 10) qui publie la taille de chunk et la borne d'archive, pour refuser un fichier trop gros dans le navigateur avant d'ouvrir un import ; les codes de refus (ceux du contrat plus `CHUNK_TOO_LARGE` et `ARCHIVE_LONGER_THAN_FILE`) deviennent des phrases avec repli générique, sur le modèle de l'export, avec un garde `Object.hasOwn` désormais partagé. La vérification passe par un journey qui fait tourner le vrai store contre une API mockée (chunks de 4 octets, archive de 10), couvrant succès, requête perdue puis `409`, fichier différent, pause/reprise, borne dépassée et démontage en cours de chunk. La description ne justifie pas ces choix face à une alternative évidente (par exemple valider la taille côté serveur seulement, ou lire l'état serveur en premier) : elle décrit l'approche sans la comparer.
