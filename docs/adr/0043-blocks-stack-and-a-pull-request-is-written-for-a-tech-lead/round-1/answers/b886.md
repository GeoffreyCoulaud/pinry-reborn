# b886

## 1. Contexte

Avant cette PR, l'application web sait suivre un import et l'annuler depuis l'écran du compte (#223), et dispose d'un store d'envoi avec ses décisions pures dans `lib/imports.ts` (#222). Le serveur expose déjà les opérations d'import : poignée de main qui publie la taille de fragment et `maxImportArchiveBytes`, `PUT` par décalage, `complete`. Il manque la partie visible pour l'utilisateur : choisir une archive et l'envoyer réellement, avec une vue de progression, des phrases pour les refus et les messages traduits. La description ne dit pas ce qui existait côté serveur au-delà de ce que les tests laissent deviner.

## 2. Pourquoi

C'est le dernier des trois morceaux du bloc 30, découpé parce qu'il mesurait 892 lignes sur 17 fichiers, au-delà du budget de 500 lignes. Sans lui, le parcours « importer une archive » du lot `the-data-travels` reste incomplet : aucun utilisateur ne peut démarrer un import depuis le navigateur. Il prépare aussi le bloc 40 (reprise après rechargement), puisqu'un envoi arrêté laisse aujourd'hui l'import en `AWAITING_ARCHIVE` sans sélecteur. La description ne donne pas de raison métier ou de calendrier au-delà de cette séquence de blocs.

## 3. Comment

Le fichier est envoyé en fragments séquentiels (`PUT` à chaque décalage, `application/octet-stream`), un seul à la fois ; sur `409` l'envoi reprend au `currentLength` du serveur, après cinq échecs réseau il se met en pause derrière un bouton de reprise, et certains cas (serveur qui détient plus que le fichier, 507) l'arrêtent avec une phrase. Les décisions restent pures dans `lib/`, dans le périmètre de couverture à 100 %, et ce bloc n'ajoute que la vue (`ImportSection.tsx`) et les phrases (`dataRefusals.ts`) ; l'envoi vit dans un store de module au-dessus du routeur, pour survivre à un changement d'écran, avec un `beforeunload` tant qu'il reste des octets. Ce qui justifie l'envoi fragmenté plutôt qu'une seule requête est implicite (survivre à une coupure réseau) mais n'est pas argumenté contre une alternative nommée ; la description ne compare ni à un envoi unique ni à un protocole existant de type tus, et renvoie à la spécification (section 9) pour la question non mesurée des connexions à moitié ouvertes.
