# b728

## 1. Contexte

Le lot `the-data-travels` ajoute l'export et l'import depuis l'écran du compte, avec un téléversement de l'archive qui peut reprendre après une interruption. Ses pull requests ne sont pas encore fusionnées. La revue d'ensemble, lancée sur le lot entier, a relevé 1 défaut MAJOR et 11 MINOR. Dans la boucle de téléversement, la requête de clôture (`POST .../archive/complete`) n'est envoyée qu'une fois, sans nouvel essai, et `IMPORT_NOT_AWAITING_ARCHIVE` est traité comme un refus : dans ces deux cas, un téléversement arrêté reste dans le store du client.

## 2. Pourquoi

Le store du client l'emporte sur l'état tenu par le serveur, dans la section Import comme dans le centre des tâches. Si la réponse à la clôture se perd, ou si un autre onglet a déjà clôturé, l'utilisateur voit un téléversement arrêté dont la seule commande est Annuler. Or Annuler envoie un `DELETE` qui supprime un import déjà `PENDING` ou `RUNNING` : c'est le MAJOR, une perte de travail. Les MINOR sont de moindre gravité : un faux message « arrêté » pendant un aller-retour après une clôture réussie, un refus d'annulation qui passe sous silence, et une lecture concurrente qui peut effacer l'enregistrement de reprise d'un import tout juste ouvert. La description ne dit pas pourquoi le correctif doit passer maintenant plutôt que plus tard, en dehors du fait que le lot se termine avec ce bloc.

## 3. Comment

Tout se passe côté web app, dans le store de téléversement (`imports.ts`) et dans une fonction d'étape pure sous `src/lib/`, donc dans le périmètre couvert à 100 %. L'API ne change pas. La clôture devient une tentative comme l'envoi d'un morceau : même délai de 5 s entre deux essais, pause au 5e échec. La boucle gagne aussi un état terminal `DONE` (« le serveur a l'archive, peu importe qui a clôturé »), atteint par une clôture acceptée ou par `IMPORT_NOT_AWAITING_ARCHIVE`. Deux règles d'ordre règlent les MINOR : le store ne se vide qu'après une nouvelle lecture du dernier import, et une annulation ne retire le téléversement qu'après un `DELETE` réussi suivi d'une nouvelle lecture. La description n'explique pas pourquoi cette voie a été préférée à l'alternative évidente, qui serait de laisser l'état du serveur l'emporter sur le store ; on peut seulement supposer qu'elle garde la logique dans du code pur et testable.
