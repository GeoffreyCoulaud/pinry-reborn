## 2. Why

Without it, a close whose answer was lost, or the losing tab of two tabs uploading one import, leaves a "stopped" upload in the store for the tab's life with Cancel as the only control, and Cancel would `DELETE` an import the server may already be running: user data at risk. Three related MINOR defects come from the store being emptied too early: a false "stopped before the end" after a success, a refused cancel that shows nothing, and a stale read deleting a fresh resume record. It is needed now because the stack is about to merge and the review's findings must be treated in the lot rather than backlogged. The description does not say why the experiment's merge figures and operator reading must wait beyond "only after the review".

## 3. How

The upload loop's decisions stay a pure function in `lib/imports.ts` (inside the 100% coverage perimeter): the close becomes one more retried attempt on the chunk schedule, and a new outcome `DONE` ("the server has moved on, read its row") replaces the stop on a `202` or `409 IMPORT_NOT_AWAITING_ARCHIVE`. The store follows one rule, an upload leaves it only after the server's replacing row has been read, which reorders close, cancel (`DELETE` first, empty only on success) and resume-record pruning. The obvious alternative, guarding against two tabs uploading one import, is rejected as an accepted known limit ("Q1"), now recorded in the backlog; the description does not argue why a pure state machine plus read-before-empty is preferred over, say, a server-side guard, beyond keeping the logic pure and testable. The `ImportsConfig` finding is kept, but its reason is in "the report below", which the description does not include.
