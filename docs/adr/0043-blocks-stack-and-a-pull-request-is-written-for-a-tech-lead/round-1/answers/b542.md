# b542

## 1. Context

The lot `the-data-travels` (the web application's data import and export, with an archive uploaded in chunks) is a stack of ten unmerged pull requests, #219 to #228, and this is its closing block on top. A holistic review run on the top of the stack before any merge found 1 MAJOR and 11 MINOR findings. The worst was in the upload flow: when the answer to `POST .../archive/complete` was lost, the upload stopped and offered Cancel, even though the server could already hold the import as `PENDING` or `RUNNING`, and that Cancel would `DELETE` it. Also missing: a flash of stale "stopped" text, a silent refused cancel, a race that pruned a fresh import's resume record, a test for a refused opening, contract-typed fixtures, one KDoc, and a specification and handoff that contradicted themselves or were incomplete.

## 2. Why

Without the MAJOR fix, a network hiccup on the close (or losing the race in the two-tabs case) could lead the user to delete an import that is actually running on the server. The lot's process has the review's findings fixed before the stack merges and the handoff freezes, and the operator asked for the review to run before their own reading. The description gives no other reason for the timing. The stack experiment's figures and the operator's reading are still missing from the handoff and must be filled before merge.

## 3. How

The fix is client-side only (`contract/openapi.json` unchanged): the server's import row becomes the authority. The close is retried on the chunks' schedule (5 attempts, 5 s apart, then pause), and `IMPORT_NOT_AWAITING_ARCHIVE` is read as "the server has moved on", so the upload gives way to the server's row once re-read instead of stopping. The decision logic stays in the pure `lib/imports.ts`: `nextStep` takes an `Attempt` (chunk or close) and gains a `DONE` step, and both requests go through one `answerOf`, which keeps it under the 100 % coverage bound. The description does not weigh the obvious alternative of a server-side guard (an idempotent close, or a lock in `appendChunk`); it only records the two-tabs case as an accepted known limit ("Q1") with no guard.
