# b223

## 1. Context

The lot *the data travels* lets a signed-in user export their data and import an archive from `/account`. The import is a resumable three-step protocol (open with `POST`, feed chunks with `PUT ...archive?offset=`, close with `POST ...archive/complete`), and the handshake from block 10 publishes the chunk size and the archive's upper bound. Block 30 was split into three pull requests. #222 built the upload store above the router and the pure decisions of its loop, and #223 built the section's read side and the cancel confirmation. What is missing is the part that starts an upload: nothing in the web application uses the store yet.

## 2. Why

Without this pull request a user still cannot start an import, because the store has no consumer. It connects the store to the screen with a file picker and an upload view, and gives every way an upload can stop (paused, refused, too large, a different file) a sentence the user reads. The description does not say why it is needed now beyond being the last third of block 30. It leaves resuming after a page reload to block 40.

## 3. How

The section takes its state from two sources, and the upload this tab holds wins over the server's latest import, because while chunks are going up the server row reads `AWAITING_ARCHIVE` and would show only a cancel button. The picker is a native `<input type="file">` with its label styled as a HeroUI button, since HeroUI has no file control. It stays disabled until the handshake answers, and it checks the size bound before opening an import, so an archive that could never fit leaves no row on the server. Refusal codes are an open set: a union of the contract's codes for the three operations plus two the loop raises itself, checked with `satisfies`, with a general fallback sentence, reusing the export's lookup made generic. The description names no rejected alternative, except that keeping the store above the router lets the upload outlive the screen, with `beforeunload` holding the page only while bytes remain.
