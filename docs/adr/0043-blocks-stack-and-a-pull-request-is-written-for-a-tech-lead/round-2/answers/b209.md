# b209

## 1. Context

The lot `the-data-travels` sits as a stack of unmerged pull requests, and the holistic review run on its top found 1 MAJOR and 11 MINOR findings. In the web application, an import archive is uploaded in chunks by a store that lives above the router and, while it holds an upload, takes precedence over the server's import row in the account screen and the task centre. The chunk loop already retries, but the closing request (`POST .../archive/complete`) was a single call outside that loop, so any failure there left a "stopped" upload in the store for the tab's lifetime with Cancel as its only control. What is missing is a retry for the close and a way to say "the server has taken over", plus corrections to the handoff, the backlog and three contradictions in the specification (the description does not say which ones).

## 2. Why

Without it, a close whose response is lost looks like a failure although the server has already moved the import to `PENDING` and will run it, so the user's only button, Cancel, sends `DELETE` on an import that is running. The tab that loses a race between two tabs uploading the same import ends in the same trap. Smaller defects sit at the same handover point: a one-round-trip "stopped before the end" message on success, a refused cancel that shows nothing, and a stale read that can delete the fresh resume record. It is needed now because the operator asked for the review before any merge, so the lot closes on these fixes; what exactly the resume record holds, and what a `DELETE` does to a running import on the server, the description does not say.

## 3. How

The close becomes one more attempt in the loop, decided by the pure `nextStep` function in `lib/` (inside the 100% coverage bound), so it inherits the chunks' retry schedule (pause after the fifth failure) and the store still only executes what `nextStep` answers. A new `DONE` step, distinct from `STOP`, covers "the server has moved on": close accepted, or `IMPORT_NOT_AWAITING_ARCHIVE` returned to either request. One handover rule follows: the upload leaves the store only after the latest import has been read again, on `DONE` and on a successful cancel, which removes the flash, keeps the refusal visible and never shows a stale row. The description does not weigh an explicit alternative (such as a special-case retry for the close in the store); the implied justification is one retry policy, with its decisions kept in pure, fully covered code rather than in the store, and it does not say how the resume-record fix works or whether the API or contract changes (only a KDoc on `maxImportArchiveBytes` is mentioned).
