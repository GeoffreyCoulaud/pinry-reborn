# b470

## 1. Contexte

La section d'import de `/account` affiche le dernier import et permet de l'annuler. L'envoi existe déjà sous forme de store au niveau du module dans `imports.ts`, qui applique les décisions pures de `lib/imports.ts` : découpage en morceaux, réconciliation sur `409 IMPORT_CHUNK_OFFSET_MISMATCH`, nouvelles tentatives, pause. Mais rien ne l'appelle : il n'y a ni sélecteur de fichier, ni progression, ni message quand un envoi s'arrête. Un utilisateur ne peut donc pas encore importer d'archive depuis l'interface.

## 2. Pourquoi

Sans ce consommateur, l'envoi par morceaux reste du code mort côté vue, et cette PR est ce qui permet à un utilisateur d'importer une archive de bout en bout. La description ne dit pas pourquoi c'est maintenant plutôt que plus tard, sinon que c'est la suite logique du store déjà livré. La reprise d'un import laissé en `AWAITING_ARCHIVE` avec le même fichier est explicitement renvoyée au bloc suivant.

## 3. Comment

La section lit deux sources, l'envoi que tient l'onglet et le dernier import du serveur, et l'envoi l'emporte, parce que la ligne du serveur ne reflète que le dernier morceau terminé. Le store vit au-dessus du routeur, donc quitter l'écran et revenir retrouve l'envoi en cours (et `beforeunload` retient la page), et c'est le store, pas la vue, qui possède la pause (après cinq requêtes perdues) et l'arrêt. Les deux bornes de la poignée de main pilotent le sélecteur : un fichier trop gros est refusé avant d'ouvrir un import, et un fichier accepté est découpé à `maxImportChunkBytes`. Les refus passent par une table ouverte avec une phrase par défaut, comme pour l'export, `hasSentence` devenant générique pour être partagé. La description ne discute aucune alternative évidente écartée, à part cette réutilisation du modèle de l'export.
