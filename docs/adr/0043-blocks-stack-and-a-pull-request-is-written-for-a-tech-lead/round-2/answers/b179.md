# b179

1. **Context.** The lot *the data travels* (import and export from the account screen) is a stack of ten pull requests, and this one closes it on top of #228; the web application's import upload lives in a module-level store above the router that outranks the server's latest import row while it holds an upload. The holistic review, run on the stack's top before any merge, found 1 MAJOR and 11 MINOR defects that nothing yet fixes, and the handoff, backlog and specification do not yet match what the stack did. The core gap is how the upload leaves that store: a lost close request (`POST .../archive/complete`) stops it for good, it is dropped before the row is re-read or before a cancel is answered, and a concurrent read of the latest import can delete a new import's resume record.

2. **Why.** Without it the lot would merge with a MAJOR: after a lost close, a stopped upload hides an import that may be `PENDING` or `RUNNING` on the server, for as long as the tab stays open, and offers only Cancel, whose one click sends a `DELETE` to a running import. The same code also flashes "the upload stopped before the end" on a success, swallows a refused cancel, and can lose a new import's resume record when the window regains focus as the file dialog closes. The operator asked for these to be fixed before their own reading and before any merge; why this closing block rather than fixes in each stacked pull request, the description does not say.

3. **How.** Two rules, both inside the store: the pure decision function in `lib/imports.ts` (inside the 100% coverage bound) now treats the close as one more attempt retried on the chunks' schedule, and reads `IMPORT_NOT_AWAITING_ARCHIVE` as "the server moved on", ending the loop like a success; and the upload leaves the store only after the latest import has been read again, a refused cancel keeping it in place and a read never pruning the tab's own resume record. Putting the decision in the pure function keeps it testable without I/O, and keeping the store's precedence while fixing when it lets go avoids the view ever showing a stale or false state. The description does not name or argue against an obvious alternative (for instance letting the server row always win, or guarding two tabs uploading one import, which the operator accepted as a known limit, "Q1"); the rest are mechanical fixes (contract-typed journey fixtures, a journey for a refused opening, catalogue cleanup, a KDoc), and one finding on an `ImportsConfig` comment is kept without a stated reason.
