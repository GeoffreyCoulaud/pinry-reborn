- Write for a tech lead who knows the project's architecture and language, has not read the specification, and will not read the code line by line.
- Give the context, then why the change is needed, then how it is done at the level of the architecture. Never describe what changed, file by file or line by line.
- Keep the visible body under 50 lines of text. A mermaid diagram's code does not count; a code block does.
- Use whatever makes the review easier: a mermaid diagram (sequence, flowchart, state, class, entity-relationship), a table, or a short code example.
- Do not comment on code quality, list risks, or list what was not verified.
- Put the block's report last, collapsed: `<details><summary>Block report, for the handoff</summary>`, then `</details>`. It holds the evidence (gate, continuous integration, budget), the departures from the plan, the tier-1 fixes, the tier-2 questions with their answers, the pitfalls and what was not verified. Lose nothing the handoff needs. The visible body repeats neither continuous integration nor the stack.
