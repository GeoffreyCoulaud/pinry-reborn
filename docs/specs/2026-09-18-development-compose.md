# The web application ships as an image, and a compose file runs the three containers

Date: 2026-09-18
Status: Approved by the operator on 2026-09-18. Two adversarial reviews closed, their thirty-two findings
recorded in this document. The second overturned the tool: its comparison measured `nginx:alpine`
where `nginx:alpine-slim` is the variant a size comparison keeps, and the choice moved from Caddy to
nginx on the operator's decision of 2026-09-18.
Branches: block 5 `chore/an-image-name-is-not-a-repository-name`, block 10
`chore/development-compose`, block 20 `chore/webapp-image-in-the-pipeline`, block 30
`chore/publish-the-webapp-image`. The repository is renamed to `pinry-reborn` between blocks 5 and
10, by hand.
ADRs: one, `docs/adr/0034-the-web-application-ships-as-an-nginx-image.md`, written in block 10. It
records the tool, not the topology: `docs/specs/2026-09-10-web-application.md` decision B already
settled "two artefacts, one reverse proxy, one public origin", and
`docs/adr/0026-one-session-two-transports.md` decision 5 records it. What no document has ever
weighed is which server serves the bundle and fronts the API. The only trace of one is the word
`Caddyfile` inside an out-of-scope row, which records no choice, and the comparison in 3.1 does not
land on it.

## 1. Goal

Run the product locally the way it is released, and release the half that has no artefact yet. The
API ships as an image and is smoked before it is published; the web application ships as nothing at
all, and the single origin its session cookie needs exists only inside Vite's development proxy.

It also stops calling the repository the API. `pinry-reborn-api` was the name when the API was all
there was; it now holds three projects (`docs/adr/0024-three-projects-share-one-repository.md`), and
two workflow lines still read an image's name out of it, which is the defect block 5 removes and the
rename would otherwise turn into a broken release path.

This lot closes "the lot that ships the web application's image", which
`docs/specs/2026-09-10-web-application.md` defers twice, at its out-of-scope row "No `Caddyfile` and
no `clients/apps/webapp/Dockerfile`" and at "the deployment documentation belongs to the lot that
ships the webapp's image".

No compose file exists. The API's image does not compile: it copies a fast jar Gradle produced
before `docker build` ran, which is what lets one Gradle build feed both architectures of a release.
The typed client is generated by the `prepare` script at install, from a path three levels above
`packages/api-client`, so a build context that carries `clients/` without `contract/` cannot
install. One image is published, and `dagger call smoke` starts it before the release path pushes
it.

## 3. The change

### 3.1 The tool

nginx `1-alpine-slim`, in both roles: the frontal proxy and the static server inside the web
application's image. The tag follows the major as every other tag here does, and it resolves to the
same digest as `alpine-slim`, which is the name the measurements below were taken under
(`docker manifest inspect`, both `sha256:578082d6635f...`). Measured on 2026-09-18, `docker pull`
then `docker images`, amd64:

| Candidate | Serves static files | Proxies | Image |
|-----------|---------------------|---------|-------|
| nginx `1-alpine-slim` (1.31.6) | `try_files`, in the always compiled core module | `proxy_pass` | **21.2 MB** |
| Caddy `2-alpine` (v2.11.4) | `try_files` and `file_server` | `reverse_proxy` | 88.8 MB |
| nginx `alpine` | as above | as above | 94.4 MB |
| Traefik | No file server; it would still need a static server behind it | yes | not measured |

The web application's image is published and pulled by everyone who installs Pinry, and the slim
variant carries a quarter of Caddy's bytes to serve a bundle of about two megabytes. Both roles then
take the same syntax, which is the other thing worth having and which no longer argues for Caddy.
What Caddy has and nginx does not, automatic HTTPS, buys nothing here: the site listens on `:6258`
with no host name, and deployment documentation is out of scope below. The frontal proxy is never
published, so revisiting it the day that documentation exists costs nothing.

Traefik is out on the first column: it routes and does not serve, so choosing it means choosing a
second server anyway.

The ADR carries this table, the sources and the two costs: seven lines against five for the static
block, one level of nesting more, and the `X-Forwarded-*` headers written by hand where Caddy sets
them itself.

### 3.2 The topology

```
proxy    nginx:1-alpine-slim, :6258 on the host
           /api/  -> api:8080
           /      -> webapp:80
webapp   the bundle, built by pnpm, served by nginx with an index.html fallback
api      api/Dockerfile unchanged, not published on the host, /data on a named volume
```

The routing lives in the frontal proxy and not in the web application's image, so that image stays
a carrier of static files: an operator who already runs Traefik or nginx puts it behind theirs
without inheriting a topology from it. This is decision B of the web application's specification,
applied.

### 3.3 The files

- **`compose.yml`**, at the root, which orchestrates the three projects as `.dagger/` does.
  `api` builds from `api/`, `webapp` from the repository root with
  `clients/apps/webapp/Dockerfile`, `proxy` takes the published nginx image and mounts `proxy.conf`
  read only. `api` carries `IMAGES_DATA_DIR`, `EXPORTS_DATA_DIR` and `IMPORTS_DATA_DIR`
  under `/data`, the image defaulting all three to `/var/lib/pinry/*`, which is the container's own
  writable layer. `DB_PATH` is already `/data/pinry.db` in the image. `proxy` waits on the API's own
  `HEALTHCHECK` with `condition: service_healthy`, and on `webapp` with a plain `depends_on`, the
  nginx image declaring no health check of its own. Both `depends_on` are load bearing rather than
  cosmetic: nginx resolves an upstream named in a literal `proxy_pass` once, at startup, and exits
  with `host not found in upstream` when the name is not up yet.
- **`proxy.conf`**, at the root, mounted at `/etc/nginx/conf.d/default.conf`: one `server` listening
  on `6258`, a `location /api/` whose `proxy_pass http://api:8080;` carries no URI of its own, and a
  `location /` passing to `http://webapp:80;`. The absent URI is the whole of it: a `proxy_pass`
  without one passes the request URI unchanged, where `proxy_pass http://api:8080/;` would replace
  the matched prefix and turn `/api/v1/pins` into `/v1/pins`
  (source: nginx.org/en/docs/http/ngx_http_proxy_module.html, read through Context7 on 2026-09-18).
  It also sets `Host` and the `X-Forwarded-*` headers, which nginx does not set on its own. The port
  is the same number inside the container and on the host, so the file and `compose.yml` name one
  number rather than a pair to translate.
- **`clients/apps/webapp/Dockerfile`**: `node:24-slim` and `pnpm@12.3.4`, the two the pipeline pins,
  copying `contract/` and `clients/`, then `pnpm install --frozen-lockfile`, the message catalogue
  compile and `pnpm --filter @pinry-reborn/webapp run build`; an `nginx:1-alpine-slim` stage copies
  `dist/` to `/srv`. The build stage is pinned to `$BUILDPLATFORM`, which is what keeps a two
  architecture build from compiling the bundle twice, the second time under emulation.
- **`clients/apps/webapp/nginx.conf`**, copied to `/etc/nginx/conf.d/default.conf`, which is where
  the image's own default sits: one `server` listening on `80`, `root /srv`, and a `location /`
  holding `try_files $uri /index.html`, which is the documented fallback for an application whose
  routes exist in the browser alone (source: nginx.org/en/docs/http/ngx_http_core_module.html, same
  reading).
- **`.dockerignore`**, at the root, for the web application's context alone, the API service
  building from `api/` under its own. Its list is `IGNORE` in `.dagger/src/index.ts` (`**/build`,
  `**/.gradle`, `**/.kotlin`, `.dagger/sdk`, `**/node_modules`, `**/dist`, `**/coverage`,
  `**/src/paraglide`) plus `api/`, `docs/`, `agents/`, `security/` and `.git`, so the two lists stay
  in step. What the context needs is 836 KB, `clients/` at 688 KB with those exclusions and
  `contract/` at 148 KB, against 2.2 GB of working tree.
- **`README.md`**, whose "Running" section gains the compose path beside the two it already carries,
  the Gradle prerequisite in the same block:
  `(cd api && ./gradlew :api-application:quarkusBuild) && docker compose up --build`. That task is
  the pipeline's own name for the artefact the image copies (`QUARKUS_BUILD` above);
  `:api-application:build` reaches it too and runs that module's tests and detekt beside it, which
  the image does not need.

### 3.4 The pipeline and the release

- **`.dagger/src/index.ts` gains `webapp-image` and `webapp-smoke`**, beside `image` and `smoke`,
  and `ci` calls them after the API's. The webapp's smoke asks the started image for `/` and for a
  path that exists in the browser alone, and expects the bundle both times. Publishing an image
  nothing ever started would be the one thing this repository refuses of the API.
- **`validate.yml`'s `publish` job gains a second metadata, build and push**, for
  `ghcr.io/geoffreycoulaud/pinry-reborn-webapp`, on the same two platforms, with the same two SBOMs
  and the same keyless cosign attestation. Three things it does not copy:
    - **No `type=semver` tag.** `docs/adr/0024-three-projects-share-one-repository.md` decision 6
      settles that the three artefacts version independently, under prefixed series `api/vX.Y.Z`,
      and the existing metadata block emits `type=semver,pattern=v{{version}}` off a `v*` tag. One
      such tag would stamp one version onto both artefacts, which is the coupling decision B cites
      as its reason for a second artefact at all. The webapp's image ships `latest` and `type=sha`
      until the prefixed series exists, which is its own lot.
    - **No `cache-to`.** The Actions cache quota is spent: about three gigabytes of engine state
      against the four the ten gigabyte quota leaves free
      (`docs/adr/0031-the-gate-builds-once-and-keeps-its-cache.md`, decision 8), and `prune` deletes
      only under the `dagger-state-` prefix, so a second `mode=max` entry would be evicted by
      GitHub's own policy and would take the state archive with it. The cost of not caching is a
      `pnpm install` per release; the cost of caching is a cold gate on every pull request.
    - **No OpenVEX predicate.** `security/vex.openvex.json` holds `"statements": []`, so attaching
      it to a second image would record nothing about it.
- **`SECURITY.md` is part of block 30.** It says today that every image pushed to
  `ghcr.io/geoffreycoulaud/pinry-reborn-api` carries three attestations and that one daily scan
  reads one SBOM. After block 30 a second image carries two attestations and no scan reads them, so
  the policy states its own shape or becomes false on merge.

**The gate gains no new check of its own, and every new file enters the ones it has.** `prose` reads
the tracked text files, the four dated series excepted (`FROZEN` in `.dagger/src/index.ts`:
`docs/specs`, `docs/plans`, `docs/adr`, `docs/handoffs`), so the long dash rule covers `compose.yml`,
both nginx configurations, the `Dockerfile`, the `.dockerignore` and `README.md`, and not the ADR block 10
writes. Blocks 5 to 30 each change a path that does not end in `.md`, so the documentation shortcut
of the root `AGENTS.md` does not apply and the full gate is paid four times.

**Block 5 is what lets the repository be renamed**, and the rename happens between it and block 10,
by hand and outside any branch: `gh repo rename pinry-reborn`, then `git remote set-url`. Two
workflow lines build an image name from the repository's, which holds only while the two coincide:
`.github/workflows/validate.yml:235` (`ref=ghcr.io/${GITHUB_REPOSITORY,,}@<digest>`) and
`.github/workflows/grype-scan.yml:48` (`IMAGE="ghcr.io/${GITHUB_REPOSITORY,,}:latest"`). The block
writes `ghcr.io/geoffreycoulaud/pinry-reborn-api` at both, which is the API's image and stays its
name whatever the repository is called, and points the VEX document's `@id` at the new URL while
bumping its `version` to 2 and its `timestamp` to the day, OpenVEX making both the document's own
counters. The `@id` is an identifier that nothing dereferences, and it is deliberately written
before the rename it names: GitHub redirects the old name to the new one and not the reverse, so the
gap is one directional and closes when the rename happens. Nothing else moves: the dated documents
keep their links, and the GHCR package is not renamed by a repository rename.

**Nothing in the gate ever runs a workflow file**, so block 5's own criterion is a grep and proves
nothing. What proves it is the rename that follows: `gh workflow run grype-scan.yml` then
`gh run watch`, the "Extract SBOM and VEX from image attestations" step reaching Grype on
`pinry-reborn-api`. That command fails if line 48 still derived the name, and the workflow accepts it
because it declares `workflow_dispatch`. Run `gh api /user/packages/container/pinry-reborn-api --jq '{repo: .repository.full_name, visibility}'`
on either side of the rename in the same pass: the two answers differ in the repository's name and
in nothing else, which is what says the package is still pushable and readable.

`dagger call gate` is condition 1 of every block. Block 10's five observations are read by hand
after `(cd api && ./gradlew :api-application:quarkusBuild) && docker compose up --build`, each
naming the output that would have proved it wrong:

1. `docker compose ps --format '{{.Service}}\t{{.Health}}'` reports `api` as `healthy`, not
   `starting` or `unhealthy`, and lists three services. Health is read here rather than through the
   proxy: `/q/health` is not under `/api/`, so a request for it reaches the web application, whose
   `index.html` fallback answers `200` to anything, which is what a correct route would look like.
2. `curl -si http://localhost:6258/api/v1/handshake` answers `200` with `content-type: application/json`.
   An `html` content type is the same failure as above, seen from the other side.
3. `curl -si http://localhost:6258/boards/does-not-exist` answers `200` with
   `content-type: text/html`, the route existing in the browser alone. The content type is the
   discriminator: a proxy misrouted the other way answers `200` here too.
4. Sign up through the interface, which `POST /api/v1/users` allows unauthenticated, then create a
   pin from a local file. The pin is displayed on the home grid.
5. `docker compose down && docker compose up` on the same named volume, then `curl -sI` on that
   pin's image URL answers `200` with an image content type. `down` removes the containers and keeps
   the volume, so bytes written into a container's own writable layer are gone by then, where the
   row in `/data/pinry.db` would survive either way and leave a grid of broken images. Naming the
   image request rather than the page is what separates the two.
6. After the block merges, and after the rename: `gh workflow run grype-scan.yml` then
   `gh run watch`, its attestation step succeeding. That is the observable that the window the
   pitfalls describe has closed, and the same command fails between the rename and this merge.

## 5. Pitfalls

- **The cookie needs `localhost`, not an address on the network.** `Secure` is unconditional
  (`docs/adr/0026-one-session-two-transports.md`), and browsers except `localhost` alone. Reaching
  the proxy at `http://192.168.x.x:6258` gives a session the browser stores and never sends.
- **6258 is free rather than merely unusual.** `grep -nE "(^|\s)6258/" /etc/services` finds nothing
  on 2026-09-18, its nearest assigned neighbours being 6253 and 6267, and it sits below the local
  ephemeral range, `/proc/sys/net/ipv4/ip_local_port_range` reading `32768 60999`. 8080 was refused
  for the collisions it invites on a development machine.
- **`docker compose build` on a stale fast jar builds a stale API in silence.** The image copies
  whatever `api-application/build/quarkus-app/` holds, and copies nothing when the directory is
  absent, which fails the build with `COPY failed` rather than a word about Gradle.
- **The web application's build context is the repository root**, the `prepare` script reaching
  `../../../contract/openapi.json`. Without the root `.dockerignore` the context carries every
  `node_modules` and the Gradle output: `du -sh --exclude=.git .` reads 2.2 GB against the 836 KB
  the build needs.
- **The API's context is 283 MB where the pipeline's is a few dozen.** `du -sh api` reads 283 MB,
  and `api/.dockerignore` deliberately keeps `**/build`, the fast jar living under one. The pipeline
  sidesteps it by building a context from the `Dockerfile` and that one directory (`imageContext`),
  which `docker compose` cannot express. Block 10 pays the upload rather than touch an ignore file
  three image tests read.
- **After block 5 no image name is derived from anything**, which is what block 30 then copies: its
  second image names itself. A line pairing one package's name with another's digest fails at the
  registry, a manifest being addressed by digest within one package, so the failure is noisy rather
  than silent; the point is that the line was never reusable.
- **The rename leaves the daily scan red until the next publication.** `grype-scan.yml` verifies the
  attestations against `${{ github.repository }}/.github/workflows/validate.yml@refs/`, and the
  attestations on the current `latest` carry the old path. Block 10 closes the window by merging:
  `release.yml` ignores `**/*.md` and `docs/**` and runs on everything else pushed to `main`, and
  block 10 writes a
  `Dockerfile` and two nginx configurations, so its merge publishes and re-signs `latest` under the
  new name.
  The window is therefore the hours between the rename and that merge, and `grype-scan.yml` runs at
  06:00 UTC. Block 5 cannot close it itself: it merges before the rename.
- **A two architecture build compiles the bundle twice unless the build stage says otherwise.**
  `FROM --platform=$BUILDPLATFORM node:24-slim` keeps it on the runner's own architecture, the
  emitted files being architecture independent, exactly as the API's fast jar is.
- **The catalogue compile in the image may be redundant.** `vite.config.ts` runs the Paraglide
  plugin, which writes `src/paraglide/` during the build; the explicit step is a net rather than a
  dependency, and block 10 drops it if the build is green without it.
- **Every image tag here follows a major, and nothing bumps them.** `nginx:1-alpine-slim`,
  `node:24-slim` and `eclipse-temurin:25-jre` all do; only `pnpm@12.3.4` is exact, and the blocks
  copy that policy rather than inventing a stricter one for the new images.
  `.github/dependabot.yml` declares its
  `docker` ecosystem at `/api` only, so no automation ever looks at a tag in
  `clients/apps/webapp/Dockerfile` or in `compose.yml`. Widening it is out of scope below.
